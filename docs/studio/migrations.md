# Studio database migrations

Studio's telemetry database uses Drizzle's native PostgreSQL migrator. The
deployment interface is unchanged:

```bash
kortyx-studio-db migrate-and-bootstrap
```

Run this as a one-shot job using the release's API image, before starting the
new application images. Back up the database first. This document covers
`@kortyx/telemetry-db`, not the SDK runtime's separate persistence migrations.

## Upgrade from the filename-based runner

The six released SQL files, `0000` through `0005`, remain byte-for-byte
unchanged. Fresh installations run that SQL through Drizzle. Existing
installations are adopted automatically:

1. Acquire the same database-scoped advisory lock used by the old runner.
2. Verify that `public.kortyx_schema_migrations` is a known contiguous prefix
   and that the Studio-owned catalog matches that prefix.
3. Atomically record those already-applied files in
   `drizzle.__drizzle_migrations`, without executing their SQL again.
4. Let Drizzle apply pending SQL and record its checksums and ordering keys.
5. Retain and complete the six-entry legacy ledger for released tooling.

Published releases contain four, five, or six legacy files. The compatibility
checks also cover prefixes zero through three, so a previously interrupted
per-file upgrade can resume. Catalog adoption checks columns, defaults,
constraints, indexes, triggers and RLS flags; it does not read customer rows.
Unrelated application tables are ignored. Catalog fingerprints are regression
tested against PostgreSQL 14 and 17; additional PostgreSQL versions need the
same compatibility tests before claiming support.

There is no database reset, key rotation, ID regeneration or operator journal
editing in the normal upgrade path. Existing legacy ledger timestamps are
preserved. A snapshot generated by Drizzle describes the deployed schema after
`0005`; historical snapshots were not invented for hand-authored SQL.

## Why a small wrapper remains

Drizzle owns SQL execution and native journal writes. Kortyx retains only
deployment locking, legacy adoption and history validation. The installed
stable Drizzle toolchain does not offer the native `pull --init` baseline
command shown in the release-candidate documentation. Adopting a verified
legacy prefix therefore needs a one-time metadata bridge, not another SQL
executor.

The installed native migrator checks the latest applied timestamp. It does
not validate the entire applied checksum prefix or acquire a deployment lock.
Kortyx validates both hashes and timestamps before allowing native migration,
rejecting modified, missing, reordered or unknown applied history.

The six legacy journal timestamps are frozen increasing ordering keys, not
historical release dates. New timestamps and snapshots come from Drizzle Kit.

## Author a migration

For normal schema changes, edit `packages/telemetry-db/src/schema.ts`, then:

```bash
pnpm --filter @kortyx/telemetry-db db:generate --name=describe_change
pnpm --filter @kortyx/telemetry-db db:check
```

For data migrations, extensions, or other SQL not modeled by Drizzle, use its
native custom-migration command and fill in the generated SQL:

```bash
pnpm --filter @kortyx/telemetry-db db:generate --custom --name=describe_change
```

Commit the SQL, journal and generated snapshot together. Review the SQL for
correct ordering and safety; generation is not proof that it will execute or
that old application replicas can use the new schema. In particular, when a
new composite foreign key references a unique index, verify that the required
unique index is created before the foreign key. Run both fresh-install and
previous-release upgrade tests for each schema change.

Never edit, remove, rename, reorder or backdate an artifact already merged to
`main`. Append a new migration instead. If two branches generate migrations
from the same head, update the unmerged branch from current `main` and
regenerate its unpublished migration. Do not rewrite published history to
resolve that collision.

Pending migrations run inside the native migrator's transaction. Do not put
`BEGIN` or `COMMIT` in migration SQL, and do not use operations such as
`CREATE INDEX CONCURRENTLY` that cannot run inside that transaction. Those
operations require a separately designed operational procedure; this runner
does not silently special-case them.

## Validation and failure handling

Public CI runs `db:check` before database migration and telemetry regressions.
With `TURBO_SCM_BASE` set, that check also compares SQL and metadata with the
base commit and rejects edits to released artifacts. No new paid runner or
private-repository CI suite is needed.

```bash
TURBO_SCM_BASE=origin/main pnpm --filter @kortyx/telemetry-db db:check
# DATABASE_URL must point to a disposable test instance; the test user needs CREATEDB.
pnpm --filter @kortyx/telemetry-db test:integration:ha
```

Tests create and remove isolated, randomly named child databases. They cover
the known legacy prefixes with seeded customer data, physical table identity,
fresh installation, reruns, concurrent jobs, compatibility with the old
advisory lock, native rollback/retry, interrupted ledger bookkeeping and
rejection of unknown or edited history. Frozen cutover fixtures remain valid
as new migrations are appended. Current schema/snapshot generation is checked
separately.

If legacy schema validation fails, adoption stops before writing a baseline
or changing product DDL. Keep the old application running, retain both
ledgers, and investigate the actual schema and matching release. Custom
changes to Studio-owned tables need explicit compatibility assessment; do
not guess a baseline or delete metadata to bypass validation.

If pending SQL fails, Drizzle rolls back the pending batch. A verified legacy
baseline may already be committed; retry resumes from it. If the job was
interrupted after native commit but before legacy bookkeeping, the next run
finishes bookkeeping without replaying SQL. Stop the rollout until the job
succeeds. Database downgrade remains unsupported; restore the matching backup
for an incompatible rollback.

## OSS and Cloud

The public schema, SQL and migration history remain authoritative for OSS.
This cutover does not compose private Cloud migrations or implement tenant
RLS. A Cloud overlay must build on this native history with an explicitly
tested release/migration ordering contract. Do not simply run two independent
Drizzle histories against the same native journal or concatenate their SQL.
